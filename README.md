# AICRATIVE

AICRATIVE is a browser-based creative prompt studio. Character, Story, Scene, Image Prompt, and Video Prompt are generated by the deterministic Local Creative Engine. It does not call an external AI provider.

## Shared password workspace

AICRATIVE uses one shared password for the entire workspace:
- No email, username, public registration, or per-user Supabase Auth login.
- Everyone who has the shared password opens the same cloud project collection.
- Anyone with workspace access can create, read, update, or permanently delete shared projects. Share the password only with trusted collaborators.

## Supabase setup

The original account/project schema and security migration should already be applied:
1. `supabase/migrations/202610300001_aicrative_accounts_projects.sql`
2. `supabase/migrations/202610310001_security_hardening.sql`

Now apply the shared workspace migration:
3. `supabase/migrations/202610310002_shared_workspace.sql`

The third migration creates `public.shared_projects`, denies direct browser-role access, and copies existing rows from `public.projects` into the shared workspace. It does not delete the original account-owned rows.

## Vercel environment variables

In Vercel → Project → Settings → Environment Variables, configure these server-only values for Production and Preview (and Development if needed). Do not prefix any of them with `VITE_`.

- `SUPABASE_URL` = Supabase Project URL.
- `SUPABASE_SERVICE_ROLE_KEY` = the legacy `service_role` JWT key from Supabase API Keys → Legacy API Keys. This key bypasses RLS and is used only by the server-side project API. Never put it in browser code, GitHub, a public build variable, or chat.
- `AICRATIVE_SESSION_SECRET` = unique random secret of at least 32 characters. It signs the access cookie; do not reuse the shared password.
- `AICRATIVE_ACCESS_PASSWORD` = strong shared password entered by all workspace users.

The old `SUPABASE_ANON_KEY` is no longer used by this shared-password backend. It may remain configured in Vercel but is not required by the new API.

Generate a session secret locally, for example in PowerShell:

```powershell
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$bytes = New-Object byte[] 48
$rng.GetBytes($bytes)
[Convert]::ToBase64String($bytes)
$rng.Dispose()
```

## Security model and limitations

- The browser submits the shared password only to `/api/access`. The server issues a signed, 30-day, Secure, HttpOnly, SameSite=Strict cookie.
- `/api/projects` validates that cookie before each database operation. Mutations also require a same-origin request.
- The service_role key is used only inside Vercel server code. It bypasses Supabase RLS, so the API authorization check is the critical security boundary. Do not expose the key or add client-side Supabase access to `shared_projects`.
- All workspace users have equal access to every shared project, including deletion. There is no per-user ownership or audit identity.
- Password throttling is in-memory per serverless instance and is best-effort. For stronger production abuse protection, add a Vercel WAF or distributed rate-limit store.
- Changing `AICRATIVE_ACCESS_PASSWORD` invalidates existing access cookies. Changing `AICRATIVE_SESSION_SECRET` also invalidates all access cookies.
- Existing rows in `public.projects` remain in place after migration as a backup. The app uses `public.shared_projects` going forward.

## Local development

Copy `.env.example` to `.env.local`, fill in the server-only values, then run:

```bash
npm install
npx vercel dev
```

Use `npx vercel dev` rather than plain Vite because the app depends on the `/api/access`, `/api/auth`, and `/api/projects` serverless routes.

Build and test:

```bash
npm run build
npm run lint
npm test
```
